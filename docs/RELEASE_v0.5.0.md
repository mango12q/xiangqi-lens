# XiangQiLens v0.5.0

本次为 4 项功能需求：**自动走棋模式互斥**、**开局库**、**天天象棋动画抑制**、
**自动接盘**。

---

## 1. 自动走棋「启动走棋 / 预览模式」改为互斥单选

原来「启用自动走棋」与「预览模式」是两个可以同时勾选的复选框，语义容易混。
现改为 **QButtonGroup 三态互斥单选**：

| 选项 | 行为 |
|---|---|
| 关闭自动走棋（默认） | 不参与落子 |
| 预览模式（只算不点） | 只显示将点击的着法与坐标 |
| 启动走棋（真点落子） | 真正模拟鼠标点击落子 |

- **不可能同时选中两种模式**（`QButtonGroup` 排他）。
- 「启动走棋」这个选择**不持久化**：重启程序一律回到关闭/预览，绝不会因为
  读了个配置文件就开始点鼠标。
- 旧版 `automove.json` 里的 `dry_run` 布尔自动迁移到新的 `mode` 三态。

## 2. 开局库（应用层实现）

官方 Pikafish 二进制**不带**开局库 —— 实测其 `uci` 输出全部选项为
`Debug Log File / NumaPolicy / Threads / Hash / Clear Hash / Ponder /
MultiPV / Move Overhead / nodestime / UCI_ShowWDL / EvalFile`，没有任何
`BookFile` 之类选项。因此开局库在本程序内实现。

### 新增文件 `app_book.py`

| 能力 | 说明 |
|---|---|
| **`.obk` 读取** | **社区实际流通的格式**（如「云霄剑诀 7.5」）。SQLite 表 `bhobk(vkey, vmove, vscore, vwin, vdraw, vlost, vvalid, vmemo, vindex)`；`vkey` 是 64 位 Zobrist（用 cchess 自带的 `cchess.zhash_data` 表算，**含行棋方**）。按 key 查询，不整库载入内存 |
| `.xqb` 读取 | [fisherfan/xqbook](https://github.com/fisherfan/xqbook) SQLite 库，**按 key 精确查询**（库自带索引），key 是位打包的棋盘布局 |
| `.txt` / `.json` | 自研线路库，手写友好：每行一条从初始局面开始的 ICCS 着法序列，支持注释与权重 |
| xqb 位级编解码 | `xqb_encode_key` / `xqb_decode_key` / `xqb_encode_move` / `xqb_decode_move` |
| obk 编解码 | `obk_zhash` / `obk_encode_move` / `obk_decode_move` |

**obk 格式逆向结论**（用真实的 `云霄剑诀7.5.obk`，170986 条记录验证）：

- 键 = cchess 的 Zobrist：起始局面（红先）= `7101337512282506414`，正是库中第 1 条的 `vkey`。
  **键含行棋方**（红先时异或 `z_redKey`）→ 不存在 xqb 那种轮次歧义。
- 着法 = `(起点偏移 << 8) | 终点偏移`，偏移是 XQWLight 的 0x88 棋盘偏移
  `0x33 + (9 - FEN行) * 16 + 列`；ICCS = `chr(97+列) + str(FEN行取反)`。
  验证：起始局面 `0xAAA7` = `h2e2`（炮二平五）；炮二平五之后（黑先）`0x3A59` = `h9g7`（马8进7）。
- ★ **生成工具的坑**：键值高位置 1（≥ 2^63）时被按 IEEE double 存进 `vkey`，
  SQLite 索引查不到。把该 double 的 8 字节原样解包即可**无损还原**原键。
  程序先走索引、查不到再 `CAST(vkey AS REAL) = ?` 全表扫（实测 4.9ms）。
- 端到端验证：从起始局面走库 14 层，每层都命中且着法全部合法。

### 新增工具 `tools/build_book.py`

用 Pikafish 自动生成 xqb：从初始局面做「宽度受限 + 深度受限」的树搜索
（`go depth D` + MultiPV，保留分差在 `--margin` 内的着法并递归），
写出社区标准 xqb。`--verify` 可只校验已有库。

已随仓库附带 `data/opening.xqb`（500 个局面 / 1930 条记录 / 生成耗时 130s）。

### 安全要点

- **只读打开**（`file:...?mode=ro`），绝不会误写用户的库文件。
- xqb 的 key **不含轮次**，因此查到的着法一律再用**严格**合法性校验过滤
  （见下文第 4 节的发现）——否则轮次判错时会拿对方的着法去点鼠标。

## 3. 天天象棋「吃」字动画抑制

**问题**：天天象棋吃子后，棋盘中间弹出「吃」字动画遮住盘面，识别结果抖动甚至
产出一个「稳定但错误」的局面，导致误判（包括判断不出对方是否走子）。

**修复**：新增**帧间运动闸门**。把拉正后的棋盘图缩成 160×144 灰度小图，逐帧
比较**变化像素占比**；超过阈值（默认 2%）即判定「画面在动」，**暂停识别**；
画面静止持续达到静置时长（默认 400 ms）才恢复。

即「**等动画消失后再识别盘面变化，有变化了再移动棋子**」——自动走棋侧读取同一
闸门状态，画面在动时一律不点击。

用「变化像素占比」而不是「平均绝对差」，是因为「吃」字只覆盖盘面中间一小块，
平均差会被大片静止区域稀释掉，占比不会。

可调：`等画面静止后再识别`（开关）/ `静置时长`（默认 400 ms）/ `变化阈值`
（默认 0.02）。

## 4. 自动接盘

一局结束后自动点击「再来一局」按钮开下一局。

### 终局判定

| 信号 | 判定 |
|---|---|
| 无**真**合法着法（将死/困毙） | 单独即可判定（唯一可靠信号） |
| 长时间停滞 | 兜底，**默认关闭**（对手认输 / 超时 / 平台弹结算框时用；可能误判） |

判定在**主循环**里每秒评估一次，而不是挂在「局面被采纳」分支上 —— 终局的
特征恰恰是局面不再变化，挂在采纳分支上**永远不会触发**（这是实现过程中发现
并修掉的 bug）。

> ⚠️ **不把「引擎报绝杀分」当判定依据**：绝杀分只说明某一方**能够取胜**，
> 不代表棋局已经结束 —— 我方即将杀棋时引擎同样报绝杀，拿它单独判定会把正常
> 对局误判成终局。它只当日志线索。

### ★ 过程中发现的一个既有认知错误（重要）

`cchess.is_valid_iccs_move` 是**伪合法**校验 —— 其源码注释原文写着
「只进行最基本的走子规则检查」，**不会**拒绝「走完之后自己被将军」或
「将帅照面」的着法。实测：`R3k3R/4R4/9/9/9/9/9/9/9/4K4 b` 这个双车杀局面里，
黑将被将军，`is_valid_iccs_move` 却对 `e9d9` / `e9f9` / `e9e8` 三个**送将**
着法全部返回 `True`。

影响：

- `app_backend.is_legal_move` / `enumerate_legal_moves` 都建立在它之上，
  因此**不可用于终局判定**；
- 项目原有文档/注释里「会完整校验……自将等规则」的说法是不准确的。

本次新增两个**严格**接口（`app_backend.py`）：

| 函数 | 用途 |
|---|---|
| `is_strict_legal_move(fen, iccs)` | 伪合法之上再要求「走完不自将、不照面」（落子 + `next_turn` + `is_checking`） |
| `has_no_legal_moves(fen)` | 真终局判定，直接用 cchess `no_moves()`（内部逐着做自将检查） |

前者用于开局库着法过滤与自动走棋，后者用于终局判定。

> `BoardTracker` 的演化校验仍沿用原来的 `is_legal_move`（伪合法）—— 它作为
> 「单帧噪声过滤器」够用，且收紧它会带来回归风险，本次**未改动**。

### 按钮模板录制（v0.5.0 实机反馈后重做）

第一版是「在目标窗口上单击一次记一个坐标」，实机反馈**没触发** —— 除了用户没标定，
更根本的问题是：天天象棋打完一局会**连弹「段位升级」「财源广进」「获得徽章」等窗口**，
把结算面板的「再来一局」挤走甚至盖住，**固定坐标点不到**。

改为**模板匹配**：

1. 点「① 框选『再来一局』按钮」→ 弹出一张目标窗口的截图 → 在图上**拖拽框住**按钮 → 存成模板 PNG。
   - 在本程序截图上框选，**完全不会误触目标窗口**。
   - 模板走 `imencode/imdecode` 读写 —— `cv2.imread` 在 Windows 上**不支持非 ASCII 路径**，
     应用目录可能含中文，会静默返回 None。
2. 点「② 框选『关闭弹窗』按钮」（可选）→ 框住弹窗的 ✕ / 「确定」。
3. 接盘时循环：找到「再来一局」就点；只找到「关闭弹窗」就先关掉、再重试（最多 8 轮）。

**用真实截图实测**：用结算面板录的「再来一局」模板，在「获得徽章」那张图上
相似度 **1.000** 命中；天天象棋各类弹窗的 ✕ 位置一致，一个模板即可关掉全部。

点击前同样有硬闸门：能把目标窗口置前、点击点确实落在窗口上（未被遮挡）。
未录模板时只提示「本局已结束」，不点击。点击后 12 秒内若未检测到新对局，
会明确提示，避免静默失败。

## 5. 新局 · 自动判断我方执子（实机反馈后新增）

**需求**：把「我方执子」改好用 —— 加一个「新局」，点了自动判断我方执子；
且点击时红方还没动子、或对局还在匹配中也要能判；选定我方执子后直接「分析」，
**去掉原来的「先手」下拉**。

### 「新局」做什么

1. **清空局面跟踪** —— 上一局的局面 / 轮次 / 计数 / 终局标记全部复位。
   不做这一步，演化校验会把新局第一帧当成「无法解释的局面」一直挡下来。
2. **自动判断我方执子** —— 依据**棋盘朝向**：识别模型给的 4 个角是内容语义的
   （`xq_vision.BONE_NAMES = A0/A8 黑方两角、J0/J8 红方两角`），而象棋客户端
   一律把**己方**摆在画面下方 ⇒ 谁的两角在下面（y 更大），谁就是我方。
   **跟「红方先手」无关，所以开局红方还没动子也能判。**
3. 对局还在匹配中、棋盘还没出现时**自动重试**，棋盘一出现立刻判定并回填下拉框。

**质量门**（必须有）：关键点检测偶尔退化（A0 跑到画面底部而 A8 在顶部、
整组点跑到画面外、四点重合）。程序要求「同边两角大致等高」+「棋盘高度足够」+
「四点都在画面内」，不满足就**拒绝判断并继续重试**，而不是瞎猜。
实测：真实截图里 8 张有 3 张关键点退化，全部被正确拒绝。

### 「先手」下拉移除 + 轮次自纠

旧版有「红方先行 / 黑方先行」下拉，和「我方执子」容易混淆，已删除。现在：

- 点过 **「新局」** → 按**规则**用「红方先手」（新局时红方还没动子，这是确定的）；
- 直接点 **「分析」** → 默认按「**轮到我方**」处理；
- **猜错也能自愈**：`BoardTracker` 新增**双方合法性自纠** ——
  某个差分着法对当前轮次不合法、但对另一方合法时，纠正轮次并采信。
  靠得住的前提：`cchess.is_valid_iccs_move` 会校验「起点格棋子颜色 == 行棋方」，
  所以同一个差分着法**不可能**对红黑双方同时合法，没有歧义。
- 自纠要**连续两次**看到同一着法才采信 —— 单帧误识别也可能恰好凑出「对另一方
  合法」的一步差分，直接采信会削弱 `BoardTracker` 赖以生存的噪声过滤。
- 自动走棋另加一道**轮次硬闸门**：若盘面还是**初始局面**、却认为轮到黑方，
  这个轮次几乎必然是猜错的（象棋红先），此时**不落子**。

这样初始轮次只影响「第一次走子之前」的显示，第一次走子后一定正确。

## 6. 「框选没反应」的根因（实机反馈修复）

**现象**：对局结束、已停止运行，点「框选『再来一局』按钮」**没有任何反应**。

**根因**：`refresh_windows` 往下拉框里存的是 **元组**
`self.combo.addItem(label, (w["hwnd"], w["title"]))`，而标定代码写成了

```python
hwnd = self.combo.itemData(idx)      # ← 这里是 (hwnd, title) 元组
self.source.attach(int(hwnd), ...)   # ← int(元组) → TypeError
```

`int((hwnd, title))` 抛 `TypeError`，而 **Qt 槽函数里的异常会被 PySide 打印到
stderr 后吞掉** —— 程序用 `pythonw` 启动没有控制台，于是表现成「点了没反应」。
**上一版的「标定」也是同一个 bug**，这解释了为什么面板一直显示「未标定」。

**修复**：

1. 新增 `_current_window()` 统一解包并返回 `(hwnd, title)`，标定与启动都走它；
2. **异常可见化**：新增 `report_exception()` + `@safe_slot` 装饰器 +
   `sys.excepthook` 兜底 —— 槽函数异常现在会写 `XiangQiLens_crash.log`
   并**弹窗提示**，不再静默失败。
