# XiangQiLens · 象棋屏幕识别与引擎分析

把棋盘从屏幕里"读"出来，交给象棋引擎分析，**在棋盘上画出推荐走法箭头**。

面向在线对局（微信小程序、桌面客户端等）的辅助分析工具：截取目标窗口画面 →
定位棋盘 → 识别 90 个交叉点的棋子 → 重建局面 → Pikafish 分析 → 显示最佳着法与候选变化。

**默认不含自动走子**：只给建议，落子由你自己操作。另有可选的「自动走棋」
（默认关闭 + 预览模式），见下文「自动走棋」一节。

## 特性

| 能力 | 说明 |
|---|---|
| **后台截图** | 用 `PrintWindow` + `PW_RENDERFULLCONTENT` 截取窗口，**不要求窗口可见、可被遮挡**；失败时自动回退到屏幕抓取 |
| **棋盘识别** | 两段式 ONNX：棋盘 4 角定位（pose）→ 透视拉正 → 90 格分类 |
| **走法箭头** | 直接画在棋盘上：绿色粗箭头是最佳着法，蓝色细箭头是候选变化 |
| **多主变例 (MultiPV)** | 引擎真实 MultiPV：同时列出 N 条主变例（分数 / 胜率 / 深度 / 中文 / ICCS），各线首着在棋盘上以蓝色细箭头标出 |
| **引擎参数面板** | Threads / Hash / MultiPV / Move Overhead / WDL 开关可实时热改，改动立刻作用于正在跑的分析；「高级」区动态列出引擎全部可调项 |
| **持续加深** | 锁定局面后 `go infinite` 持续加深，主变例随深度实时刷新（不重传棋盘图像，开销很小） |
| **崩溃自愈** | 引擎进程意外退出时自动重建并用当前局面重开搜索，分析不中断 |
| **胜率显示** | 开启引擎的 `UCI_ShowWDL`，显示「我方胜率 58% · 和 30% · 对方 12%」及局面判断（自动按我方执子方换算视角） |
| **中文着法** | `h2e2` → `炮二平五` |
| **轮次推断** | 识别只能看局面、看不出轮到谁走，用局面差分 + 引擎着法合法性自纠推断 |
| **朝向自适应** | 识别模型的角点是内容语义的（黑方两角/红方两角），无论谁在画面下方都自动得到标准朝向，不需要人工翻转 |
| **新局 · 自动判断我方执子** | 点「新局」清空上一局残留，并按「己方棋子在画面下方」自动判断我方执子 —— 开局红方还没动子、或对局还在匹配中也能判 |
| **轮次自纠** | 该谁走不用手动设：观察到第一次走子时按「双方合法性」自动纠正轮次 |
| **四道识别闸门** | 见下文「识别流水线」，任何一道不过都不会把垃圾局面送进引擎 |
| **失败可见** | 左栏显示识别程序**实际看到的棋盘**；窗口最小化等异常会明确提示原因 |
| **自动走棋** | 轮到我方时取引擎最佳着法，**模拟鼠标点击**落子（纯 Win32 用户态，无驱动、无内存注入）；「关闭 / 预览 / 真点」三态**互斥单选**，**默认「启动走棋（真点）」**，见下文 |
| **开局库（可选）** | 应用层实现的开局库：支持社区实际流通的 **`.obk`**（如「云霄剑诀」）与 `.xqb`，以及自研 `.txt/.json` 线路库；库着优先或仅提示。官方 Pikafish 二进制不带开局库，见下文 |
| **动画抑制** | 帧间变化像素占比超阈值即暂停识别，等画面静止到设定时长再继续 —— 修复天天象棋吃子「吃」字动画遮挡盘面导致的误识别 |

## 快速开始

### 方式 A：下载预编译版（推荐，无需 Python）

从 [Releases](https://github.com/mango12q/xiangqi-lens/releases/latest) 下载最新版的
`XiangQiLens-vX.Y.Z.zip`，解压后双击 **`XiangQiLens.exe`**。

> ⚠️ 请**解压后整目录使用**，不要只把 exe 单独拷出来 ——
> exe 需要同级的 `xq_research/` 提供识别模型与引擎（约 95MB）。

系统要求：Windows 10/11 64 位。

### 方式 B：从源码运行

需要 Python 3.10+（开发环境为 3.13）。推荐用 DirectML 版 onnxruntime 走 GPU：

```bash
pip install PySide6 opencv-python numpy mss pywin32 cchess
pip install onnxruntime-directml     # Windows + 任意显卡；纯 CPU 用 onnxruntime
```

> **性能差异很大**：默认的 `onnxruntime` 是 CPU 版，即使代码里请求 CUDA 也会静默降级。
> 实测识别耗时 CPU 版约 980ms/帧，DirectML 版约 170ms/帧。详见下文「性能」。

然后下载模型与引擎（见下节），再运行：

```bash
python app_vision.py
```

Windows 下也可以直接双击 **`启动XiangQiLens.bat`**：用 `pythonw.exe` 无窗口拉起界面，不弹黑框。
排错时改用 `启动XiangQiLens.bat debug`（控制台前台运行，报错看得见）；启动器不自带解释器路径时，
会依次回退到 `PATH` 里的 `pythonw.exe` 和 `py -3`。

自检（不启动界面，验证环境是否正常）：

```bash
python app_vision.py --selftest
```

### 操作步骤

1. 把对局窗口开到棋盘可见
2. 在「目标窗口」下拉框里选**棋局窗口本身**（如 `JJ象棋 [Chrome_WidgetWin_0]`、
   `天天象棋 [Chrome_WidgetWin_0] WeChatAppEx.exe`），不要选整个聊天/宿主窗口
   —— 棋盘占比太小会导致角点定位失败。
   列表已过滤掉系统壳 / 输入法 / 显卡服务等无关窗口，程序还会**自动选中**
   最像棋局窗口的那一项（标题含「象棋」或宿主是微信小程序进程），通常不必手动挑
3. **「我方执子」** —— 决定左栏盘面朝哪边、自动走棋「只走我方」的闸门。
   点 **「新局」** 会自动判断（见下方说明），也可以手动选。
4. （可选）展开右栏「引擎参数」调线程 / 哈希 / 多主变例 / 落子延时，或勾选「持续加深」
5. 点 **「分析」**

#### 新局 · 自动判断我方执子

新开一局时点 **「新局」**：**停掉当前分析**并清空局面跟踪（否则上一局的局面 /
轮次 / 计数残留会把新局的第一帧当成「无法解释的局面」一直挡下来），
然后**由你点「分析」重新开始**（刻意不自动开始，什么时候开局由你决定）。
点「分析」时会**自动判断我方执子**。

判断依据是**棋盘朝向**：识别模型给的 4 个角是内容语义的
（`xq_vision.BONE_NAMES = A0/A8 黑方两角、J0/J8 红方两角`），而象棋客户端一律把
**己方**摆在画面下方 —— 谁的两角在下面（y 更大），谁就是我方。**跟「红方先手」
无关，所以开局红方还没动子也能判**。

对局还在匹配中、棋盘还没出现时会自动重试，棋盘一出现立刻判定并回填下拉框。

> 关键点检测偶尔会退化（例如 A0 跑到画面底部、A8 在顶部，或整组点跑到画面外）。
> 程序要求「同一条边的两角大致等高」+「棋盘有足够高度」+「四点都在画面内」，
> 不满足就**拒绝判断并继续重试**，而不是瞎猜。

#### 关于「该谁走」（原来的「先手」下拉已移除）

旧版有个「先手」下拉（红方先行 / 黑方先行），容易和「我方执子」混淆，现已删除。
现在：

- 点过 **「新局」** → 按**规则**用「红方先手」（新局时红方还没动子，这是确定的）；
- 直接点 **「分析」** → 默认按「**轮到我方**」处理；
- **猜错也能自愈**：`BoardTracker` 会在观察到走子时做**双方合法性自纠** ——
  某个差分着法对当前轮次不合法、但对另一方合法时（**连续两次**看到同一着法，
  避免把单帧噪声当成「轮次反了」）直接纠正轮次。
  前提：`cchess.is_valid_iccs_move` 会校验「起点格棋子颜色 == 行棋方」，
  所以同一个差分着法**不可能**对红黑双方同时合法。
- 自动走棋另有一道**轮次硬闸门**：若盘面还是初始局面、却认为轮到黑方 ——
  这个轮次几乎必然是猜错的（象棋红先），此时**不落子**。

| 选项 | 决定什么 | 选错的后果 |
|---|---|---|
| **我方执子** | 左栏盘面朝哪边 + 自动走棋只走我方 | 左栏朝向反着、自动走棋不动（**局面识别本身不受影响**） |
| 该谁走 | 首帧轮到谁 | 首次分析给出的着法不对，**之后第一次走子就会自动纠正** |

> 早先的版本认为「执黑时画面上下颠倒、必须翻转矩阵」，于是按「我方执子」把 90 格矩阵
> 旋转 180°。这是**错的**：识别模型的关键点本身就是内容语义的
> （`xq_vision.BONE_NAMES = A0/A8 黑方两角、J0/J8 红方两角`），
> 拉正流程已经把黑方底线摆到 row 0 —— 无论哪一方在画面下方，模型输出都已是标准朝向。
> 再翻一次会把局面翻反（黑将落到 row 9），被「局面严格校验」判成
> `黑将在九宫外 (9,4)`，每帧都挡下，状态栏只会一直刷
> 「局面变化无法解释，已挡下（已挡 N 帧）」。
> 现在矩阵不再按这个选项翻转，只在遇到模型输出异常（黑将真的在下方）时自检兜底翻转一次。
> `tools/probe_tracker_branches.py` 可以验证闸门的各个分支。

## 识别流水线

每帧识别结果要依次通过四道闸门，任何一道不过都不会送进引擎：

| # | 闸门 | 检查内容 | 为什么需要 |
|---|---|---|---|
| 1 | **棋盘几何校验** | 四角构成的四边形：边长、宽高比、面积占比 | pose 模型在**画面里没有棋盘时也会输出 4 个点**，且常退化成一条线。实测在 JJ象棋 主界面的 3D 棋盘摆件上，输出四角的 y 只差 18px |
| 2 | **局面严格校验** | 将帅各一、各兵种数量上限、将帅在九宫、将帅不照面、总子数 ≤ 32 | `cchess` 对缺子/多子局面很宽松，实测会接受「两个黑将、没有红帅」；而 Pikafish 遇到非法局面**直接退出进程** |
| 3 | **棋规校验** | 用 `cchess` 构造并生成合法着法 | 兜住闸门 2 未覆盖的规则 |
| 4 | **演化校验** | 新局面必须能由上一局面走**一步合法着法**得到 | 挡住单帧误识别。不满足时暂存为候选，连续两帧一致才采信；连续 6 帧仍无法解释则兜底采信（避免卡死）并提示 |

其中闸门 4 是提升可用性的关键 —— 单帧把红傌读成红炮这类错误，一旦采信整局分析都会跑偏。

```
帧1: 采信(初始局面)   红方走  建议 b2e2 炮八平五
帧2: 挡下(drop)      ← 识别飘了，被挡住
帧3: 采信(稳定新局面)  红方走  建议 b0c2 马八进七
帧4: 采信(走子)       黑方走 ← 轮次正确翻转
帧5-6: 挡下(drop)
护栏: 已挡 3 帧 · 着法序列 ['b2d2']
```

## 性能

识别性能关键在 **execution provider**。实测（JJ象棋窗口 683×1253）：

| 配置 | pose | cls | 推理合计 | 完整单帧 |
|---|---|---|---|---|
| `onnxruntime`（CPU 版） | 13.8ms | **872.5ms** | 885.7ms | 979ms |
| `onnxruntime-directml` | **4.1ms** | **128.0ms** | **132.3ms** | **170ms** |

DirectML 版还显著更稳：CPU 版 p90/中位 = 1.35（偶发 1170ms 尖峰），DirectML 版 1.06（实测 120~154ms）。

> 首帧有约 **3 秒预热**（DirectML 编译着色器），之后才进入稳定速度。

确认当前用的哪个 provider：

```bash
python tools/bench_vision.py --runs 20
```

## 实现要点

**坐标系统一**：进程启动即设 Per-Monitor V2 DPI 感知。不做这一步，高缩放下
`GetWindowRect` / 截图坐标会整体差 1.5 倍。

**后台截图**：`PrintWindow` 必须带 `PW_RENDERFULLCONTENT (0x2)`，否则 CEF / DirectX
渲染的窗口（微信小程序、Electron 应用）会截出空白图。

**箭头坐标**：由着法的 ICCS 坐标经识别所用透视矩阵反算，与棋盘像素级贴合。
`h0h5` 换算结果 `from=(356.25,450.00) to=(356.25,227.78)`，实测起止点均落在棋子中心。

**轮次推断**：识别产物只有局面、没有"轮到谁走"这一位信息。两条途径补齐 ——
局面差分推进（相邻局面恰好差一步合法着法则翻转轮次），以及引擎着法合法性自纠
（Pikafish 只从当前行棋方视角给着法，若其着法仅对另一方合法则说明轮次设错）。

## 已知限制

- **识别会偶发出错**。模型在个别棋子/皮肤上会误判（例如把红傌读成红炮）。闸门 4
  能挡住瞬时错误，但若某次误判连续稳定出现，兜底机制会在 6 帧后采信它。
  判断方法：看左栏显示的棋盘，那就是程序实际"看到"的画面。
- **轮次依赖开局**。从对局中途接手时，初始轮次靠「先手」选项猜，之后靠引擎自纠一次。
- **窗口不能最小化**。最小化时 `GetWindowRect` 只返回标题栏尺寸，截图拿不到棋盘。
  程序会检测并提示，但不会替你还原窗口。
- **仅 Windows**。截图、DPI 与窗口状态检测都依赖 Win32 API。

## 关于引擎能力

本工具调用的是官方 [Pikafish](https://github.com/official-pikafish/Pikafish)，
分析质量取决于引擎本身。实测其 UCI 选项（2026-09-06 版）：

```
Threads / Hash / Clear Hash / Ponder / MultiPV / Move Overhead
nodestime / UCI_ShowWDL / EvalFile / NumaPolicy / Debug Log File
```

注意**没有** `Repetition Rule`、`ScoreType`、`Skill Level` 这些选项 —— 网上一些
象棋引擎（如网页版）会对自身构建额外加这些扩展，官方二进制不含。

界面显示用到的两项：

- **`UCI_ShowWDL`**（已默认开启）：让引擎在 `info` 行输出
  `wdl 72 917 11`（红方视角的胜/和/负，千分比），据此显示胜率。
  没有它就只能从 centipawn 用 `50 + 50*tanh(cp/470)` 估算。
- **`MultiPV`**：候选着法列表就是靠它拿到的（取引擎 info 里不同 pv 首着）。

引擎的分数有两种含义，别混淆：`score cp` 是**当前行棋方视角**，
而 `wdl` 是**红方视角**。程序内部按我方执子方做了统一换算。

## 自动走棋（默认开启）

开启后：识别到**轮到我方**且局面稳定 → 取引擎最佳着法 → **模拟鼠标点击**
「起点 → 终点」替我落子。对手仍在真实平台上下棋，本程序不动对方棋子。

### 怎么做到的

与 [babalae/better-genshin-impact](https://github.com/babalae/better-genshin-impact)
的 `MouseEventSimulator` 同一路线：`user32!SetCursorPos` 移动光标 +
`user32!mouse_event` 发左键按下/抬起。**纯 Win32 用户态调用，无驱动、无内存注入、
不读写目标进程内存**。

坐标换算复用识别链路已有的透视矩阵 —— 引擎着法 `h2e2` → `move_arrow()` 反算得到
**原截图坐标** → 叠加抓帧时的窗口矩形原点 → **屏幕物理坐标**。进程已设
Per-Monitor V2 DPI 感知，无需缩放换算。

### 使用步骤

1. 右栏展开「自动走棋」面板，**走棋模式**是**互斥单选**：`关闭` / `预览模式（只算不点）` / `启动走棋（真点落子）`；
2. **默认就是「启动走棋（真点落子）」** —— 点「分析」就会真的替你落子；
3. **第一次用建议先切到 `预览模式（只算不点）`**：观察右栏 / 状态栏显示的
   「将点击的着法与屏幕坐标」，确认坐标落在正确交叉点上；
4. 确认无误后再切回「启动走棋（真点落子）」。

> 三态互斥意味着**不可能同时选到两种模式**。选择会存进 `automove.json`，
> 下次启动沿用；想彻底停掉就选「关闭自动走棋」，或直接按「紧急停止自动走棋」。

> 首次使用建议先用 `python tools/test_click_coord.py` 生成
> `analysis/click_preview.png`（在原截图上标出点击点，不点击），肉眼核对坐标。

### 安全闸门

只有**全部**满足才会点击：

- 轮到我方（`my_side`），且起点格确实是**我方棋子**；
- 局面已通过四道识别闸门且稳定（连续 N 帧一致）；
- **画面已静止**（动画抑制闸门认为稳定）—— 动画/落子过程中一律不点；
- `bestmove` 属于**当前**局面（不是上一次搜索的残留）；用开局库时，库着必须
  通过**严格**合法性校验（含自将 / 将帅照面）；
- 同一局面同一着法**只点一次**；两次落子间隔 ≥ 冷却时间；
- 目标窗口未被最小化、能被置前，且**两个落点都确实落在目标窗口上**
  （`WindowFromPoint` 校验，防止点到别的程序）；
- 抓帧后窗口未被移动/缩放（否则透视矩阵失效，放弃本次）；
- 连续走子数未超「保险丝」上限。

其它保障：点击未生效会自动重试，超过上限则**自动停止并提示**；
「紧急停止自动走棋」按钮只关自动走棋、不终止识别；
「启用」开关**不持久化**，每次启动都从关闭状态开始。

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| 思考时间 | 1200 ms | 自动走棋专用，强制**限时搜索**（`go infinite` 永不返回确定着法，无法用于落子） |
| 落子方式 | 两次点击 | 点起点选子 → 点终点落子；部分界面只认「拖拽」时可切换 |
| 落子冷却 | 1.5 s | 两次落子最小间隔 |
| 最大连续走子 | 200 | 保险丝，达到后自动停止 |
| 移动插值步数 | 1 | 光标移动步数；界面要求「悬停」才响应时可调到 4~8 |
| 点击后恢复光标 | 关 | 落子后把鼠标移回原位 |

参数保存在应用目录下的 `automove.json`（已在 `.gitignore` 中）。

### 限制

- 点击是**前台物理点击**：会抢占真实鼠标，目标窗口必须**可见且能置于前台**；
  窗口被遮挡或无法置前时会跳过本次并提示（识别本身仍可后台进行）。
- 平台若禁止自动化操作，请遵守其用户协议。

## 开局库（可选）

**为什么在应用层做**：官方 Pikafish 二进制**不带**开局库。实测它 `uci` 输出的
全部选项只有 `Debug Log File / NumaPolicy / Threads / Hash / Clear Hash /
Ponder / MultiPV / Move Overhead / nodestime / UCI_ShowWDL / EvalFile` ——
没有任何 `BookFile` 之类的库选项（Stockfish 官方也没有，只有 Polyfish 等分支才有）。
所以库在 XiangQiLens 里实现：**先查库，命中就用库着，不命中再交给引擎**。

### 支持的格式

| 格式 | 说明 |
|---|---|
| `.obk` | **社区实际流通的格式**（如「云霄剑诀 7.5」）。SQLite 表 `bhobk(vkey, vmove, vscore, vwin, vdraw, vlost, vvalid, ...)`；`vkey` 是 64 位 **Zobrist**（用 cchess 自带的 `cchess.zhash_data` 表算，**含行棋方**）。按 key 查询，不整库载入内存 |
| `.xqb` | [fisherfan/xqbook](https://github.com/fisherfan/xqbook) 格式。SQLite，key 是**位打包的棋盘布局、不含轮次** |
| `.txt` | 自研线路库，每行一条线路（从初始局面开始的 ICCS 着法序列），`#` 注释、行首 `*N` 指定权重 |
| `.json` | 同上，`{"lines": [["h2e2","h9g7"], {"moves":[...], "weight":3}]}` |

> **obk 的键含轮次**（红先时异或红方标志），所以没有「同一布局红黑两轮次命中同一批
> 着法」的歧义；xqb 的键不含轮次，查到的着法一律再用**严格合法性**校验过滤一遍
> （含自将/照面）——否则轮次判错时会拿对方的着法去点鼠标。

> ⚠️ **obk 生成工具的一个坑**（已兼容）：键值高位置 1（≥ 2^63）时，生成工具把它按
> IEEE double 存进了 `vkey`，SQLite 索引查不到，必须 `CAST(vkey AS REAL)` 全表扫才
> 命中。程序两种形式都试（实测全表扫 4.9ms），不会丢数据。

### 生成自己的库

```bash
# 约 2 分钟，产出 500 个局面 / 约 2000 条记录
python tools/build_book.py --out data/opening.xqb

# 更深的库（更慢）
python tools/build_book.py --out data/opening-deep.xqb \
    --depth 16 --ply 8 --width 4 --margin 30 --max-positions 600

# 只校验已有库
python tools/build_book.py --verify data/opening.xqb
```

原理：从初始局面做「宽度受限 + 深度受限」的树搜索 —— 每个局面跑
`go depth D`（MultiPV = W），保留与最优着法分差在 `--margin` 内的着法，
再递归到下一层，结果写成社区标准 xqb。

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| 启用开局库 | 关 | 需先选择库文件 |
| 库着策略 | 库着优先 | 「库着优先」= 命中时「当前建议」与自动走棋都用库着；「仅提示」= 只显示、不影响走棋 |
| 库深度 | 40 手 | 只在前 N 手内用库；0 = 不限制 |

## 识别稳定（动画抑制）

**解决什么**：天天象棋吃子后，棋盘中间会弹出「吃」字动画，遮住盘面。动画期间
识别结果会抖动甚至产出一个「稳定但错误」的局面，导致误判（包括判断不出对方
是否走子）。

**怎么解决**（面板里默认**关闭**，需要时勾选）：把拉正后的棋盘图缩成 160×144 灰度小图，逐帧比较**变化像素占比**
（阈值默认 2%）。占比超阈值即认为「画面在动」（吃子动画、落子动画、窗口刷新等），
**暂停识别**；画面静止持续达到「静置时长」（默认 400 ms）才恢复。

即需求里的「**等动画消失后再识别盘面变化，有变化了再移动棋子**」——
自动走棋侧也读同一个闸门状态，画面在动时一律不点击。

> 用「占比」而不是「平均绝对差」，是因为「吃」字只覆盖盘面中间一小块，
> 平均差会被大片静止区域稀释掉，占比不会。

| 参数 | 默认 | 说明 |
|---|---|---|
| 等画面静止后再识别 | **关** | 总开关（按需求默认关闭；需要时勾上） |
| 静置时长 | 400 ms | 画面须持续静止这么久才恢复识别；动画长就调大，嫌慢就调小 |
| 变化阈值 | 0.02 | 变化像素占比阈值；误报多调大，漏检动画调小 |
